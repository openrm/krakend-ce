# Fork scope decisions

This repo used to carry a broad set of openrm-specific patches on top of upstream `krakend-ce`, split across two long-lived branches (`v1`, `chore/v2-middlewares`). We're moving to track upstream more closely and keep only what's actually worth the ongoing maintenance cost. This file records, per custom feature, what we decided and why, and **exactly how each one differs from stock krakend-ce's default behavior** — so a future maintainer doesn't have to re-derive it, and can check every claim against the cited source file/function directly.

A rebase spike (`spike/rebase-v2.13`, based on upstream `v2.13.11`) confirmed the whole custom `custom/` patch bundle builds and links cleanly on current upstream — 475 lines changed across 11 files.

**Correction log (2026-09-25):** an earlier version of this file contained several claims that turned out to be wrong on direct re-verification against source. Recording them here rather than quietly fixing them, because the pattern matters more than any single line:
- The `error_namespace` feature was marked "recommend drop, 0 usage" based on a compound grep whose sub-patterns were never individually re-checked. Real count: 41 usages across 5 projects (fixed 2026-09-24).
- The `custom/render.go` renderer was marked "likely dead" because a grep searched for a JSON field called `"render"` — which isn't the real field name. KrakenD selects a custom renderer via `output_encoding`. Real count: 38 usages across 8 projects, largely the *same* endpoints as `error_namespace`.
- The bloom-filter revocation "vs stock" comparison (namespace `auth/revoker`, in-process, no server) was carried over from an earlier session's web search and never independently checked against the actual stock module source. The real stock namespace and architecture are both different — see below.
- The log-redaction "if dropped" consequence was stated as a leak risk ("headers may leak into logs unredacted"). Tracing the actual code path found the opposite: the custom formatter is what *introduces* header-logging in the first place; without it, gin's stock formatter never logs headers at all. The six affected production configs are logging *less*, not leaking more.

All four are corrected below, with the source paths that back each claim.

## Decision (2026-09-25): stop litigating feature-by-feature, keep everything the spike proved out

Per-feature keep/drop analysis kept producing costly, repeated errors (see correction log above) without changing much of the outcome — the spike had already shown every feature below except `krakend-amqp` RPC rebases and builds cleanly on `v2.13.11`. Simplified to: **carry everything forward unchanged**, except `krakend-amqp` RPC (didn't port cleanly, confined to `testing` only — dropped for now, revisit if it turns out to matter) and `krakend-cel`'s own addition (already dead code regardless, no reason to carry it). Sections below are kept as the record of what each feature actually is and how it differs from default, not as a live decision queue.

## Bloom-filter token revocation — Keep

**Vs default, corrected:** stock krakend-ce's own revocation mechanism lives in `github.com/krakend/bloomfilter/v2/krakend` (imported directly in `executor.go` as `krakendbf`), registered under namespace **`github_com/devopsfaith/bloomfilter`** (source: `bloomfilter/v2/krakend/krakend.go:18` — not `auth/revoker` as an earlier version of this doc claimed, secondhand from a web search that was never checked against the actual module). Its `Register()` function (same file, line 33) does more than "in-process": it calls `server.New(ctx, rpcConfig.Config)` and `register(serviceName, rpcConfig.Port)` — **stock's revocation is also an RPC server with a listening port**, not a pure in-process filter fed only from JWT claims. The real architectural difference from `openrm/krakend-bloomd` is role, not existence-of-a-server: stock has each KrakenD instance run its *own* listening RPC server (something else pushes revocations *to* it); `openrm/krakend-bloomd` instead makes KrakenD a *client* connecting *to* one shared external `bloomd` C-server (`~/dev/bloomd`, a fork of `armon/bloomd`). Whether that shared/centralized-vs-per-instance distinction matters here depends on how revocations actually get pushed today (not something I've traced) — the two are more similar in shape than previously written, but not identical.

Decided permanent regardless — used by 8 of 13 gateway projects for JWT revocation, and switching architectures is a real infra change, not just a config rename.

Cost of keeping it, measured for real: the krakend-ce-side hook is trivial (2 commits, ~14 lines, in `executor.go`/`go.mod`). The real cost was that the *published* `openrm/krakend-bloomd` module (`v2.0.0-alpha`, its only release) hardcoded a dependency on an old `krakendio/krakend-jose/v2 v2.0.4` purely for one interface type (`jose.Rejecter`), and that old jose version is now broken by unrelated `gocloud.dev` upstream churn (a removed `OpenCensusViews` export) — this would break on *any* modern build today, independent of this migration. Fixed directly in `~/dev/krakend-bloomd`: repointed the dependency at `github.com/krakend/krakend-jose/v2 v2.12.3` (2-line change), confirmed it builds standalone and the full `krakend-ce` binary links against it.

## JWT auto-refresh + redirect-on-401 — Keep

**Vs default, verified against source:** stock krakend-jose's validator, on any failure (missing token, expired, bad signature, rejected by a rejecter), calls `c.AbortWithStatus(http.StatusUnauthorized)` and stops — source: `gin/jose.go` in the stock `krakend/krakend-jose/v2@v2.12.3` module, lines 136/146/154/184. That's it: a bare 401, no body, no `Location` header, no retry. The `github.com/openrm/krakend-jose` fork adds `refresh_url`, `refresh_property`, `refresh_cookie_key`, `refresh_cookie_domain`, `redirect_on_unauth_to` on top of that — on a 401, instead of just aborting, it calls `refresh_url` with the refresh cookie, and either replays the request with a new token or issues a redirect to `redirect_on_unauth_to`. None of this exists in stock at all.

Blast radius is not evenly spread: it's the *primary* auth mechanism for `comps` (24/25 endpoints) and `admin` (15/19, plus a `sysAdmin` role gate), heavy in `ml` (9/10), but only a single endpoint each in `openroom`, `video`, `enterprise`.

Porting cost, measured: the patch itself is small and well-isolated (9 commits, 270 lines across 5 files — two new files, `refresher.go`/`status_rejecter.go`, plus small hooks in the gin/mux adapters). Needed two small fixes to build against current upstream (an old-JWT-library import swap, and a dead `gocloud.dev` re-export to delete) — both applied and confirmed building, uncommitted in `~/dev/krakend-jose`.

This is the one item where "cheap to port" doesn't mean "cheap to drop" — it's a real, security-relevant auth flow for the heaviest-traffic projects, not a convenience feature. If dropped, the recommended replacement is moving the refresh/redirect logic to the frontend/BFF layer rather than trying to replicate it as a lightweight gateway plugin (the token-refresh-and-retry half needs to rewrite and replay the request, which is closer to re-implementing a validator).

## Domain-tagged backend errors (`error_namespace` + `combiner: status` + `output_encoding: json_error`) — Keep

This was previously three separate, mis-assessed items (a "recommend drop" status-handler claim with a false 0-usage count, and a "likely dead" renderer claim with a wrong field name). They're actually one cohesive feature chain, used together, and genuinely load-bearing. Corrected counts, from direct re-checks:

- `error_namespace`: **41 usages** — `enterprise` 9 (×3 env files), `ocr` 22 (single templated file), `sharing` 7, `comps` 2 (×3), `admin` 1 (×3).
- `output_encoding: json_error`: **38 usages**, across `enterprise`/`admin`/`comps`/`sharing`/`ocr` — the same feature's other half.
- `combiner: status`: **4 usages**, all in `ocr` (`/v1/onepagers/`, `/v1/pdf/split`, `/v1/split-pdf/`, `/v2/onepagers/`) — needed only where a single endpoint aggregates *multiple* backends and their statuses need reconciling into one.

**How the chain works, and vs default, traced through stock lura source (`github.com/luraproject/lura/v2@v2.14.2-...`):**

1. A backend status handler decides what counts as "OK." Stock (`transport/http/client/status.go`): default is exactly 200 or 201, anything else becomes a generic `ErrInvalidStatusCode` with no name, no body, no status code attached to it as data (line 69). Stock *also* already has a close analogue to `error_namespace`, under the **same** extra_config namespace (`github.com/devopsfaith/krakend/http`, aliased as `client.Namespace`): a `return_error_details: "<name>"` field that produces a `NamedHTTPResponseError{Code, Msg (raw string body), Enc, name}` (`status.go` lines 122–132, 179–187). The custom `error_namespace` field (`custom/status.go`) does almost the same thing under a different field name in the same block, but JSON-decodes the backend's response body into a structured value instead of keeping it as a raw string, and its `.Error()` message is a generic `"request failed with status %d"` instead of the raw body text (stock's `.Error()` returns the raw body). **This is the one real, precise difference** — not "namespace tagging disappears," but "the captured error body goes from a parsed object to a raw string, and the error message text changes."
2. Any error implementing a 3-method `responseError` interface (`Error() string`, `Name() string`, `StatusCode() int`) — satisfied by both stock's `NamedHTTPResponseError` and the custom `ResponseError` — gets specially caught in `proxy/http.go` (line ~122): instead of failing the whole backend call, it's turned into `Data["error_<name>"] = <the error>` plus `Metadata.StatusCode = <code>`, and the call is treated as *successful* at the proxy layer. Stock's own un-named variant (`return_error_code: true` → plain `HTTPResponseError`, no `Name()` method) does **not** satisfy this interface and does *not* get this treatment — it just fails the backend call outright.
3. When an endpoint aggregates multiple backends, something has to decide the *overall* response's status. Stock's default combiner (`proxy/merging.go`, `combineData`) merges everyone's `Data` maps together but **never reads or sets `Metadata.StatusCode` at all** on the merged response. The custom `combiner: "status"` (`custom/combiner.go`) is what actually copies a part's `Metadata.StatusCode` up to the overall response.
4. Finally, something has to put that status code on the wire. Stock's default JSON render (`router/gin/render.go`, `jsonRender`) calls `c.JSON(status, ...)` using `status := c.Writer.Status()` — i.e. whatever gin's writer already has, which for an untouched context defaults to 200. **Stock's default render never looks at `Metadata.StatusCode` at all on the success path.** The custom `output_encoding: json_error` renderer (`custom/render.go`) is what actually does `c.JSON(response.Metadata.StatusCode, response.Data)`, making step 3's aggregated status real. (Side note found while tracing this: `output_encoding: "no-op"` already gets this for free via stock's own `noopRender`, which does `c.Status(response.Metadata.StatusCode)` unconditionally — so any no-op-encoded endpoint doesn't need the custom renderer at all for this specific behavior.)

**Net effect of dropping the whole chain:** backend failures on all 41 tagged endpoints stop producing a distinguishable, per-domain error in the response body, and on the 4 `ocr` multi-backend endpoints the aggregated HTTP status reverts to whatever gin defaults to (200, unless something else sets it). A near-equivalent stock field (`return_error_details`) exists for the single-backend, single-error case — migrating those 41 call sites to it would keep the overall mechanism working with a body/`.Error()`-message shape change, without carrying the martian fork's `NewRequestExecutorFactory` extraction forward at all. The 4 multi-backend `combiner: status` cases in `ocr` have no stock replacement — that part would need to stay custom, or be redesigned.

## Custom access-log formatter (`header_blacklist`/`trace_header`/`skip_paths`) — Keep

**Vs default, corrected:** `custom/logging/logging.go`'s `GetFormatter` returns a `gin.LogFormatter` that is wired into the router's access-log middleware via `Formatter: customlogging.GetFormatter(cfg)` in `executor.go` (passed to `router.EngineOptions`, which lura's `router/gin/engine.go` forwards straight into `gin.LoggerWithConfig`). Read closely, **this custom formatter is what introduces full-header logging in the first place** — it unconditionally includes `"headers": filterHeaders(r.Header, blacklist)` in every structured JSON log line it produces (`logging.go` line 88); `header_blacklist` only controls which of those headers get replaced with `"[Filtered]"` (line 40–52), not whether headers are logged at all.

Stock behavior when this formatter isn't active: `gin.LoggerWithConfig` (vendored `gin-gonic/gin@v1.9.1`, `logger.go` line 204–206) falls back to gin's own `defaultLogFormatter`, which logs only timestamp/status/latency/clientIP/method/path — **no headers, ever, custom or otherwise** (confirmed by reading `defaultLogFormatter`, lines 132–151).

**This directly changes an earlier, wrong claim about severity.** The production configs using the dead key `github_com/openrm/logging` (missing `krakend-`) — `admin`, `video`, `comps`, `ml` (as of 2026-09-25; `openroom` and `fs` had this too, already fixed during their Track B migrations) — don't leak unredacted headers into logs, as previously stated. `ConfigGetter` fails to find config under the wrong key, `GetFormatter` returns `nil`, and gin silently falls back to its own plain-text formatter that never logs headers in the first place. The real consequence of the dead key is different and smaller: those projects' production logs (a) aren't in the structured "logstash" JSON format the others get, and (b) don't get `skip_paths` applied, so health-check/noise paths aren't excluded either. Worth fixing as a real bug (wrong key, inconsistent log format/volume) — just not the security issue it was described as.

Porting cost: trivial. The whole feature is self-contained in `custom/logging/logging.go` (101 lines), no forked third-party module to track — it's pure krakend-ce-side code.

**The same "missing `krakend-` prefix" bug exists for two other features, found while migrating `video` (2026-09-25) and confirmed with a full repo-wide search rather than fixed one project at a time:**
- **Bloom-filter revocation**: the real namespace is `github_com/openrm/krakend-bloomd` (confirmed in `~/dev/krakend-bloomd/bloomd.go`). `video` (both `krakend.production.json` and `krakend.staging.json`), `admin` (`krakend.production.json`), and `ml` (`krakend.production.json`) instead use `github_com/openrm/bloomd` — token revocation is silently inert in those environments today, independent of anything in this migration.
- **Sentry**: the real namespace is `github_com/openrm/krakend-sentry` (confirmed in the actual `krakend-sentry` module, `sentry.go:12`). `video/krakend.production.json` instead uses `github_com/openrm/sentry` — Sentry error capture has never actually been active there.

Neither of these is a new custom feature to evaluate — they're the same already-decided (Keep) bloomd and Sentry features, just silently non-functional in a few environments due to a config typo. Fixed for `video` directly as part of its Track B migration; `admin`, `comps`, `ml` still have their respective instances of this bug, independent of when their migrations happen.

## Sentry error capture — Keep

No official Sentry plugin exists for krakend-ce; stock has no error-reporting integration at all beyond whatever gets written to the configured log output. Used in 6/13 projects. Porting cost: trivial (2 commits, 11 lines, in `handler_factory.go`/`router_engine.go`). Cheapest replacement path if dropped: route error-level log lines through the existing structured log pipeline into Sentry instead of a gateway-native plugin.

## `config-watcher` — Keep

**Vs default:** stock krakend-ce reads its config file once at process start; there is no file-watching or hot-reload built in at all. `config-watcher` is a small companion tool that watches the config file and restarts/reloads KrakenD on change, for local dev convenience only. Investigating `~/dev/krakend-watch` found it isn't even a real fork — `origin` points straight at `krakend/krakend-watch` with zero local commits, it's the unmodified official tool. Already documented as broken on macOS today (README's own known-issues section) — part of the team already works without it. Cost to "keep" is effectively zero; recorded as open only because no one has confirmed whether it's still wanted at all.

## `krakend-amqp` RPC support — Drop for now

**Vs default, verified against the actual module krakend-ce depends on** (`github.com/krakend/krakend-amqp/v2@v2.3.1-0.20260317155713-...`, fetched from the real proxy, not assumed): stock `produce`/`consume` are fire-and-forget — `produce` publishes a message and returns immediately; `consume` receives messages independently. Stock's `producer.go` does have a `reply_to_key`/`ReplyTo` field (line 40/99) that sets an AMQP `ReplyTo` header on the outgoing message, so a downstream consumer knows where to send a reply — but that's just tagging the message, not blocking the original HTTP request for a correlated response. **There is no `rpc.go` in current upstream at all** — the synchronous request-blocks-until-correlated-reply pattern is genuinely openrm-only.

Used by exactly one project's config, `testing` — 4 of its endpoints (`/v1/users`, `/v1/organizations`, `/v1/rabby/new`, `/v1/rabby/link`) use `github.com/devopsfaith/krakend-amqp/rpc`; a 5th (`/health/custom`) uses stock `.../produce`, unaffected either way. Did **not** port cleanly in the spike (upstream `client.go`/`consumer.go` have real structural drift beyond just the RPC addition: header propagation, NOOP-encoding support, connection-close handling all reshaped) — deferred, needs a dedicated porting pass if kept.

**Verified precisely what happens on the rebased binary without it**, rather than leaving it vague: stock `krakend-amqp`'s backend factory (`client.go`, `func (f backendFactory) New`) tries `initConsumer` then `initProducer`; neither recognizes the `rpc` extra_config key, so both fail and it falls through to `f.bf(remote)` — the plain, non-amqp-aware backend factory. That factory would attempt a real HTTP request against the literal backend host, which is an `amqp://guest:guest@...` URL — not a silent no-op, an actual failed request at call time (invalid scheme for an HTTP client). Lowest-stakes item to actually drop if the porting effort isn't worth it, given the single-project blast radius.

## Custom tracecontext propagation (`krakend-opencensus` fork) — Keep

**Vs default, partially verified — flagging the boundary honestly:** stock `HTTPRequestExecutorFromConfig` (`krakend/krakend-opencensus/v2@v2.2.1`, `http.go` line 27) always wraps the backend HTTP call in an opencensus span via `trace.NewContext(ctx, fromContext(ctx))` — so *local* trace linkage (within the same process, across middleware) happens either way. What I confirmed: the fork's addition threads an explicit `propagation.HTTPFormat` value through to the request's `Transport`, which is opencensus's mechanism for serializing trace context into **outgoing HTTP headers** sent to the backend (cross-process propagation). What I have **not** independently verified: exactly what stock's `ochttp.Transport` does when its own `Propagation` field is left nil — whether it sends no propagation header at all, or falls back to some opencensus-internal default format. Wired in unconditionally (`backend_factory.go`/`handler_factory.go` call the propagation-aware variant directly, not behind a per-endpoint opt-in), across all 13 projects. If dropped, worst case is backend hops lose cross-process trace-context propagation (a tracing-quality regression); best case, if stock already has a sane default, the difference is smaller than that. Porting cost: trivial (12 lines), already ported cleanly onto current upstream in the spike.

## `krakend-cel` fork's own addition — Recommend drop

Already tracks upstream via merged dependabot PRs. Its one own commit ("Expose rejecter with statuses") backs a CEL-based JWT rejecter that is, notably, **already disabled** in the current patch bundle (`executor.go` has it commented out under "Disable default rejecter"). Recommend dropping the fork and depending on stock `krakend-cel` directly — the stock library is genuinely load-bearing elsewhere (`validation/cel` backs the grade-gating used by `cel_grade.tmpl` across `third`/`agents`/`openroom-v2`/`ocr`/`comps`/`admin`/`enterprise`), but that usage doesn't touch the fork's own addition at all.
